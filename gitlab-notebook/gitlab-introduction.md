# GitLab 介绍与自建代码仓库选型指南

> 本文用于帮助个人或团队了解 GitLab 的主要能力，并判断是否适合搭建 GitLab Self-Managed（自托管实例）。文中功能和资源要求参考 GitLab 官方文档，整理日期为 2026 年 7 月 20 日；具体功能可能因版本和订阅等级而不同，部署前应再次核对官方说明。

## 一、GitLab 是什么

GitLab 是一个以 Git 仓库为核心的软件研发协作平台。它不仅能保存和管理源代码，还把需求管理、代码评审、自动化测试、构建、发布、安全扫描、制品管理等环节整合在同一个系统中。

GitLab 主要提供三种使用方式：

- **GitLab.com**：由 GitLab 官方托管，注册后即可使用，无须自己维护服务器。
- **GitLab Self-Managed**：部署在自己的服务器、私有云或公有云账号内，由使用方负责安装、升级、备份、安全和监控。
- **GitLab Dedicated**：由 GitLab 提供的单租户托管方案，主要面向有较高隔离和合规要求的大型组织。

对于“自建代码仓库”这一需求，通常讨论的是 GitLab Self-Managed。

## 二、GitLab 的主要特性

### 1. Git 代码仓库管理

GitLab 支持通过 SSH 或 HTTPS 克隆、拉取和推送代码，并提供：

- 项目、群组和子群组管理；
- 公共、内部和私有可见性设置；
- 用户、角色和分级权限控制；
- 分支、标签、Git LFS、代码浏览及提交历史；
- 受保护分支、受保护标签、推送规则和签名提交；
- 项目导入、导出、镜像和归档。

这些能力能够减少误推送、强制覆盖生产分支以及未授权修改等风险。GitLab 还可以把分支规则、合并权限、审批规则和 `CODEOWNERS` 结合起来，对关键代码建立更严格的保护流程。

### 2. Merge Request 与代码评审

GitLab 使用 Merge Request（简称 MR，合并请求）承载代码变更和评审过程。在一个 MR 页面中，团队可以查看代码差异、提交记录、流水线状态、评论和是否满足合并条件。

常用能力包括：

- 行级评论、讨论和变更建议；
- 指定负责人和评审人；
- 将 MR 与 Issue 关联，并在合并后自动关闭 Issue；
- 根据流水线、冲突、评审结果等条件控制是否允许合并；
- 使用 MR 模板统一变更说明；
- 在付费等级中配置更细致的必需审批规则和代码所有者审批。

它的价值不只是“把代码合进去”，而是保留某项修改由谁提出、为何修改、经过哪些检查以及由谁确认的完整记录。

### 3. 项目与研发任务管理

GitLab 内置 Issue、标签、里程碑、迭代和 Issue Board，可用于管理缺陷、需求和开发任务。Issue Board 可以按状态、标签、负责人或里程碑组织卡片，支持看板和 Scrum 等工作方式。

团队可以形成一条相对完整的追踪链：

```text
需求或缺陷（Issue）
        ↓
开发分支与提交（Branch / Commit）
        ↓
代码评审（Merge Request）
        ↓
自动检查（CI/CD Pipeline）
        ↓
版本与部署（Release / Deployment）
```

此外，项目 Wiki、Markdown 文档和 Pages 等功能也可用于沉淀研发文档。不同版本与订阅等级支持的计划管理能力存在差异。

### 4. 内置 CI/CD

GitLab CI/CD 通过仓库根目录中的 `.gitlab-ci.yml` 定义流水线。代码推送、创建 MR、定时任务或手工操作都可以触发流水线。

流水线由多个 Stage 和 Job 组成，可实现：

- 代码格式检查和静态分析；
- 编译与单元测试；
- 构建容器镜像或软件包；
- 部署到测试、预发布和生产环境；
- 保存测试报告和构建产物；
- 按分支、标签、文件变化或变量决定执行条件。

Job 由 GitLab Runner 执行。Runner 可以部署在 GitLab 服务器之外，并按项目隔离资源。这样既能控制构建环境，也能避免大量编译任务与 GitLab 主服务争抢 CPU、内存和磁盘。

### 5. 制品与镜像管理

GitLab 可以为项目提供容器镜像仓库，也可以作为多种开发生态的私有软件包仓库。官方文档列出的软件包格式包括 Maven、npm、NuGet、PyPI、Go、Composer、Conan、Helm 和通用包等。

因此，源代码、流水线和构建后的镜像或软件包可以共享同一套用户权限与项目边界，减少另行搭建制品平台的需求。需要注意的是，流水线产物、软件包和容器镜像增长较快，必须设置保留策略、清理策略和容量告警。

### 6. 安全与合规能力

GitLab 可把安全检查接入开发流水线，包括静态应用安全测试（SAST）、密钥检测、依赖扫描、容器扫描、动态应用安全测试（DAST）和 API 安全测试等。

这些能力有助于把问题提前暴露在 MR 或流水线阶段。不过，扫描结果展示、漏洞管理、策略强制执行和合规功能在不同订阅等级之间差异较大，不能默认认为免费版包含全部高级安全能力。

### 7. 集成和自动化

GitLab 提供 REST API、GraphQL API、Webhook、访问令牌以及大量第三方集成。团队可将其连接到身份认证、通知、监控、项目管理、云平台和部署系统，也可以通过 API 自动创建项目、管理成员或读取流水线状态。

## 三、自建 GitLab 的好处

### 1. 数据和访问边界可控

代码、Issue、评审记录、构建日志及制品可以保存在组织控制的网络和存储中。管理员可以决定实例能否访问公网、由哪些身份系统登录、备份存放在哪里，以及日志保留多久。这对内网开发、保密项目、离线环境和有数据驻留要求的组织尤其重要。

需要强调的是，“数据在自己服务器上”不自动等于安全。补丁、账号、密钥、网络、备份和审计管理不到位时，自建实例同样会产生严重风险。

### 2. 研发工具链更集中

Git 仓库、Issue、MR、CI/CD、软件包和容器镜像可以集中在一个平台，减少多个系统之间重复配置账号、权限、Webhook 和项目映射的工作。研发人员也能从 Issue 一直追踪到代码、流水线和发布结果。

### 3. 可按组织需要定制

自建实例可以控制域名、邮件、Runner、对象存储、备份策略、登录方式、网络入口和可用的集成功能。对于只允许内网访问或需要连接内部 LDAP、监控、制品库和部署平台的团队，这种可控性很有价值。

### 4. 自动化能力完整

GitLab CI/CD 与 MR、权限及仓库事件天然集成，较容易实现“提交代码—自动测试—人工审批—自动发布”的流程。统一的平台也能减少集成故障点和工具切换成本。

### 5. 可从免费等级起步

GitLab Self-Managed 提供 Free、Premium 和 Ultimate 等等级。团队可以先使用免费功能验证工作流，再根据审批、安全、合规和支持需求评估付费方案。选型时应以官方当期的功能对照和许可条款为准，而不能把付费功能算入免费部署收益。

### 6. 支持隔离网和离线环境

GitLab 官方提供离线安装指导，因此在无法连接公网的研发网络中也可以部署。但安装包、依赖、Runner 镜像、安全规则库及升级介质需要建立专门的离线同步流程，运维复杂度会明显增加。

## 四、GitLab 是否适合自建代码仓库

### 结论

**适合，但前提是团队确实需要平台化研发能力，并且有人持续负责运维。**

如果需求是内部代码托管、规范化评审、自动化构建发布、细粒度权限或数据留在自有环境，GitLab Self-Managed 是成熟且完整的选择。如果只需要为少量人员保存 Git 仓库，或者团队没有服务器运维能力，GitLab 往往过重，托管服务或 Gitea、Forgejo 等轻量方案可能更经济。

### 适合自建的情况

- 源代码不能放在第三方多租户平台；
- 需要在内网或隔离网络中使用；
- 希望代码、评审、任务、流水线和制品统一管理；
- 需要自定义登录、权限、网络、Runner 或备份策略；
- 项目和成员数量较多，希望统一研发规范；
- 有运维人员或团队，能够长期承担升级、备份、监控和故障恢复。

### 不太适合自建的情况

- 只有几个小仓库，需求仅限于 Git push 和 pull；
- 没有人能持续维护服务器和数据库；
- 业务希望零维护、快速开始，并可接受使用公有云服务；
- 服务器、备份、监控和人力成本高于数据自主管理带来的收益；
- 团队已经有稳定的 CI、项目管理和制品系统，不希望再整合或迁移。

### 简明选型表

| 需求或条件 | 建议 |
| --- | --- |
| 只需要简单的私有 Git 仓库 | 优先考虑轻量自建方案或托管服务 |
| 需要 MR、Issue 和基础 CI/CD | GitLab Self-Managed Free 值得评估 |
| 代码必须留在内网 | GitLab Self-Managed 较合适 |
| 需要强制审批、高级安全与合规 | 评估 GitLab Premium 或 Ultimate 的功能和成本 |
| 没有专职或兼职运维人员 | 优先使用 GitLab.com 等托管服务 |
| 已有 Kubernetes，但缺少相关运维经验 | 不建议仅为 GitLab 引入 Kubernetes 部署 |
| 希望统一完整研发工具链 | GitLab 的综合优势较明显 |

## 五、自建需要承担的成本与风险

### 1. 资源成本

GitLab 相比单纯的 Git 服务占用更多资源。GitLab 当前官方安装要求把单节点 **8 vCPU、16 GB 内存**作为基准，并说明内存受限环境最低可在 8 GB 内存上运行。应用节点还需预留约 40 GB 基础空间，仓库、数据库、构建产物、软件包和容器镜像需要另行计算。

这些数字是部署评估起点，不是所有场景的固定最低配置。实际容量取决于用户数、仓库规模、并发请求和流水线负载。生产环境宜使用 SSD，并将 Runner 的计算与缓存需求单独估算。

### 2. 持续运维成本

自建后至少需要维护以下事项：

- GitLab 版本升级和安全补丁；
- HTTPS 证书、域名、邮件和身份认证；
- 数据库、仓库存储、对象存储及磁盘容量；
- GitLab Runner 的升级、隔离和弹性；
- 日志、性能、队列、错误率和容量监控；
- 定期备份、异地副本及恢复演练；
- 用户生命周期、权限审计和失效令牌清理。

### 3. 备份并不等于可恢复

GitLab 的备份可覆盖数据库、Git 仓库、上传文件、软件包、流水线产物等数据，但外部对象存储和配置密钥可能需要单独备份。官方还要求恢复目标与备份使用兼容的版本和版本类型。生产环境必须定期执行恢复演练，不能只检查“备份任务成功”。

### 4. 免费版与付费版边界

基础代码托管、MR、Issue 和 CI/CD 已能满足许多团队，但强制审批、部分高级计划管理、安全仪表盘、漏洞治理、合规策略、Geo 和企业支持等能力可能需要更高订阅等级。应先列出必需能力，再对照最新功能表核算许可证，而不是先部署后才发现关键流程需要付费。

## 六、推荐的落地方式

### 小型或初次部署

对于希望先验证 GitLab 的小型团队，可以采用以下思路：

1. 使用一台独立 Linux 服务器，通过官方 Linux 软件包安装。官方将这种方式描述为成熟、易安装和易升级的部署方式。
2. GitLab 主服务与 Runner 分开部署，避免构建任务影响代码访问和 Web 服务。
3. 配置 HTTPS、SMTP、管理员双因素认证、注册限制和最小权限。
4. 将备份复制到另一台主机或独立对象存储，并完成至少一次恢复演练。
5. 为仓库、日志、构建产物、软件包和镜像分别设置容量告警与清理策略。
6. 先以少量非关键项目试运行，确认权限、MR、流水线和恢复流程后再迁移重要仓库。

Docker 也可用于部署 GitLab；如果团队更熟悉主机软件包运维，生产环境通常从官方 Linux 软件包开始更直接。Kubernetes/Helm 方案适合已有成熟 Kubernetes、外部 PostgreSQL、Redis 和对象存储能力的团队，不应仅为了运行 GitLab 而增加不必要的基础设施复杂度。

### 上线前检查清单

- [ ] 明确实例负责人和故障联系人；
- [ ] 确认域名、HTTPS、邮件和登录方式；
- [ ] 禁止不必要的公开注册，启用多因素认证策略；
- [ ] 设计群组、项目和角色权限模型；
- [ ] 保护默认分支，并建立 MR 评审规则；
- [ ] Runner 不使用不受信任的共享高权限执行环境；
- [ ] 估算仓库、LFS、产物、包和镜像的容量增长；
- [ ] 配置自动备份、异地保存和恢复演练；
- [ ] 建立升级前备份、测试和回退流程；
- [ ] 核对免费与付费功能边界及总拥有成本。

## 七、最终建议

GitLab 的核心优势是把代码仓库升级为一个端到端研发协作平台。它适合对代码控制、研发流程、持续交付和内部集成有明确需求的团队。自建可以获得数据和基础设施控制权，但这种控制权同时意味着持续的安全与运维责任。

可以用下面一句话作出初步判断：

> **如果团队需要“代码托管 + 评审 + CI/CD + 权限治理”的一体化平台，并且愿意承担持续运维，自建 GitLab 值得选择；如果只需要一个 Git 远程仓库，则应优先考虑更轻量的方案。**
