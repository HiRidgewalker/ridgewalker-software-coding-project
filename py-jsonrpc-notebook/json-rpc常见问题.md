# JSON-RPC 常见问题

## 什么是 JSON-RPC

JSON-RPC 是一种轻量级的远程过程调用协议。它的核心思想是：客户端通过发送一段 JSON，告诉服务端要调用哪个方法、传什么参数；服务端执行后，再返回结果或错误信息。

JSON-RPC 2.0 的典型请求格式如下：

```json
{
  "jsonrpc": "2.0",
  "method": "getUser",
  "params": {
    "id": 123
  },
  "id": 1
}
```

成功响应：

```json
{
  "jsonrpc": "2.0",
  "result": {
    "id": 123,
    "name": "Alice"
  },
  "id": 1
}
```

失败响应：

```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32601,
    "message": "Method not found"
  },
  "id": 1
}
```

JSON-RPC 的常见特点：

- 面向方法调用，而不是面向资源。
- 消息格式简单，适合快速实现和调试。
- 传输层不固定，可以运行在 HTTP、WebSocket、stdio、TCP 等之上。
- 支持 notification，即只发请求、不要求返回结果。
- 支持 batch，即一次发送多个调用。

## JSON-RPC 的协议结构是统一的还是自定义的

JSON-RPC 的协议结构是统一规范的，但业务内容是自定义的。更准确地说，JSON-RPC 是“统一协议骨架 + 自定义业务内容”。

统一的部分主要是协议外壳，也就是消息格式本身。JSON-RPC 2.0 规定了请求和响应的基本结构，例如：

- 请求对象通常包含 `jsonrpc`、`method`、`params`、`id`
- 成功响应使用 `result`
- 失败响应使用 `error`
- `result` 和 `error` 不能同时出现
- 响应中的 `id` 应与请求中的 `id` 对应

此外，JSON-RPC 还统一规定了一些协议级能力：

- notification：没有 `id` 的请求，服务端不返回响应
- batch：可以一次发送多个请求
- 标准错误码：例如 `-32700`、`-32600`、`-32601`、`-32602`、`-32603`

自定义的部分主要是业务接口内容，也就是你自己的方法设计。例如：

- 方法名由你定义，如 `get_user`、`run_task`、`deploy_service`
- `params` 内部字段由你定义，如 `user_id`、`task_name`
- `result` 里的业务数据结构由你定义
- 业务错误码和业务错误信息也可以由你定义

例如下面这个请求，统一的是 JSON-RPC 外壳，自定义的是业务方法和参数：

```json
{
  "jsonrpc": "2.0",
  "method": "get_user",
  "params": {
    "user_id": 1
  },
  "id": 100
}
```

这里：

- `jsonrpc`、`method`、`params`、`id` 属于协议规定的结构
- `get_user` 和 `user_id` 属于业务层自定义内容

可以把 JSON-RPC 理解成一个固定格式的消息壳。壳的格式是标准化的，但壳里面装什么方法、参数和业务返回值，由你的系统自己决定。

## RESTful API、gRPC、JSON-RPC 的区别

可以把三者理解为三种不同的接口设计思路：

- RESTful API：把系统看成一组资源，通过 HTTP 方法来操作资源。
- gRPC：把系统看成一组强类型的远程函数。
- JSON-RPC：把系统看成一组用 JSON 表达的远程方法调用。

| 维度 | RESTful API | gRPC | JSON-RPC |
| --- | --- | --- | --- |
| 核心模型 | 资源 | 远程函数 | 远程方法 |
| 常见数据格式 | JSON | Protobuf | JSON |
| 类型约束 | 较弱 | 很强 | 较弱到中等 |
| 性能 | 中等 | 高 | 中等 |
| 调试体验 | 好 | 一般 | 好 |
| 浏览器友好度 | 很好 | 一般 | 取决于传输层 |
| 公开 API 适配度 | 很适合 | 一般 | 一般 |
| 内部服务通信 | 可以 | 很适合 | 可以 |
| 命令式接口表达 | 一般 | 适合 | 很适合 |

## 什么场景下使用 RESTful API

RESTful API 更适合资源管理型系统，也就是业务对象天然可以表示为“资源”的场景，例如用户、订单、商品、文章、评论等。

常见适用场景：

- 典型 CRUD 系统。
- 面向前端页面或移动端的 Web API。
- 面向第三方开放的平台接口。
- 需要充分利用 HTTP 生态的系统，例如网关、缓存、代理、监控、鉴权等。

典型风格示例：

- `GET /users/123`
- `POST /orders`
- `PUT /products/42`
- `DELETE /comments/9`

适合选 RESTful API 的原因：

- URL 和 HTTP 方法都比较直观，容易理解。
- 很贴合 Web 开发习惯。
- 对浏览器和第三方开发者更友好。
- 文档、调试和接入工具成熟。

不太适合 REST 的情况：

- 接口本质上不是操作资源，而是执行动作。
- 需要表达很多命令式行为，例如 `approveInvoice`、`runTask`、`startJob`。
- 需要强类型契约和高性能服务间调用。

## 什么场景下使用 gRPC

gRPC 更适合内部服务之间的通信，尤其是对性能、类型约束、跨语言协作有明确要求的场景。

常见适用场景：

- 微服务之间的高频调用。
- 对低延迟、高吞吐有要求的内部链路。
- 多语言系统之间共享统一接口定义。
- 需要客户端流、服务端流或双向流的场景。

适合选 gRPC 的原因：

- 接口定义清晰，通常基于 Protobuf，类型约束强。
- 性能通常优于基于 JSON 的普通 HTTP API。
- 客户端和服务端代码生成成熟。
- 原生支持流式通信。

不太适合 gRPC 的情况：

- 需要直接面向浏览器或第三方开发者开放接口。
- 希望接口能被人手工快速调试和阅读。
- 团队更依赖 HTTP/JSON 生态，而不是 IDL 和代码生成。

## 什么场景下使用 JSON-RPC

JSON-RPC 更适合命令式、方法式接口，而不是资源式接口。它强调“调用哪个方法”和“传什么参数”，而不是“操作哪个资源”。

常见适用场景：

- 区块链节点接口，例如查询余额、发送交易、调用合约。
- IDE、编辑器、语言服务器等工具链通信。
- 插件系统、桌面应用、本地进程间通信。
- 通过 WebSocket 建立的双向命令通道。
- 设备控制、远程命令执行、内部工具平台。

这类接口往往更像下面这样的方法调用：

- `compileProject`
- `runTest`
- `getBalance`
- `deployContract`
- `subscribeEvents`

适合选 JSON-RPC 的原因：

- 很适合表达“动作”或“命令”。
- 使用 JSON，阅读和调试成本低。
- 比 gRPC 更轻量，不要求复杂的 IDL 和代码生成流程。
- 可以灵活运行在多种传输层之上。

不太适合 JSON-RPC 的情况：

- 需要一个非常标准化、对外普遍易懂的开放 API。
- 需要像 gRPC 那样强约束的接口定义和类型系统。
- 团队缺少统一约定，导致方法命名、错误码、版本管理容易混乱。

## 什么是 stdio

这里容易和 `studio` 混淆，但在技术语境里通常说的是 `stdio`，不是 `studio`。

`stdio` 是 `standard input / standard output` 的缩写，通常还会连着 `stderr` 一起出现：

- `stdin`：标准输入，程序从这里读取数据。
- `stdout`：标准输出，程序把正常结果写到这里。
- `stderr`：标准错误输出，程序把日志或错误信息写到这里。

在 JSON-RPC 场景里，`stdio` 通常表示两个本地进程通过标准输入和标准输出直接通信，而不是通过 HTTP 端口通信。

一个简化的通信关系可以理解为：

```text
主程序  --写入 stdin-->  子程序
主程序  <--读取 stdout-- 子程序
```

例如主程序发送一条 JSON-RPC 请求：

```json
{
  "jsonrpc": "2.0",
  "method": "ping",
  "params": {},
  "id": 1
}
```

子程序返回：

```json
{
  "jsonrpc": "2.0",
  "result": "pong",
  "id": 1
}
```

`stdio` 很适合以下场景：

- IDE 启动语言服务器。
- 编辑器插件和后台进程通信。
- CLI 工具和本地 worker 进程协作。
- 桌面程序调用本地子进程。

与其他传输方式的直观区别：

- HTTP：适合跨网络的请求-响应调用。
- WebSocket：适合长连接和双向实时通信。
- stdio：适合同一台机器上的本地进程通信，不需要暴露网络端口。

## 怎么快速选型

如果只想记一套实用判断标准，可以按下面的方法选择：

- 对外开放、资源管理、Web 生态优先：选 RESTful API。
- 内部微服务、强类型、高性能、流式能力优先：选 gRPC。
- 命令式接口、工具链通信、JSON 调试友好、本地进程通信：选 JSON-RPC。

也可以从业务建模角度快速判断：

- 业务更像“资源”：优先考虑 RESTful API。
- 业务更像“服务函数调用”：优先考虑 gRPC。
- 业务更像“远程方法或命令调用”：优先考虑 JSON-RPC。
